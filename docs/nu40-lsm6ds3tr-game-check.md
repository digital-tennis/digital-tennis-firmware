# NU40 센서 입력 → 기존 테니스 게임 확인

이번 PR은 센서 입력만 다룹니다. Unity 코트 스킨은 [별도 PR #31](https://github.com/digital-tennis/digital-tennis-game/pull/31), AirBand 웹 실험은 [별도 저장소 PR #1](https://github.com/hex-aragon/air-band/pull/1)입니다. 게임 스킨을 병합하지 않아도 기존 게임으로 센서 연동을 검수할 수 있습니다.

## 모델 확인이 먼저입니다

사용자가 알려준 이름은 `LSM6DS3TR`입니다. 여기 추가한 어댑터는 **LSM6DS3TR-C 전용 후보**입니다. 부품/구매 명세의 `-C` 유무를 아직 실물로 확인하지 않았습니다. LSM6DS3/TR, DSL, DSO를 같은 칩으로 간주하지 않습니다. WHO_AM_I가 0x6a라는 사실만으로 모델을 확정할 수도 없습니다.

LSM6DS3TR-C가 맞으면 공식 [ST 데이터시트 DocID030071 Rev 3](https://www.st.com/resource/en/datasheet/lsm6ds3tr-c.pdf)를 기준으로 전용 폴링 경로를 사용합니다. ID 검사, 제한시간이 있는 SW_RESET, 설정 읽기 검증, 가속도/자이로 새 샘플 확인과 한 번의 12바이트 읽기를 수행합니다. 416Hz ±16g/±2000dps 데이터를 기존 100Hz 취득 경계에 공급하고, 가속도는 m/s², 각속도는 deg/s로 변환합니다. 실패한 읽기는 출력 샘플을 갱신하지 않습니다.

다른 모델이면 이 overlay를 사용하지 말고 정확한 모델의 드라이버를 검토합니다. 기존 LSM6DSO overlay와 일반 Zephyr sensor API 경로는 그대로 남겨 두었습니다. 기본 빌드는 센서 연결을 가정하지 않습니다.

## 실물 담당자가 확인할 항목

- 센서와 breakout의 정확한 품명/리비전, 보드 리비전, 공급·논리 전압, 공통 GND.
- 실제 SDA/SCL 핀, SA0 연결과 I2C 주소(0x6a 또는 0x6b), 장착 XYZ 방향.
- `overlays/nu40-lsm6ds3tr-c.overlay.example`의 P0.26/P0.27과 0x6a는 **이전 AirBand 인수자료에 따른 예시 가정**이며 이 게임 펌웨어로 측정한 배선이 아닙니다. 실제 값으로 검토한 `.overlay`를 별도로 만듭니다. 주소를 바꾸면 `imu@...`와 `reg`를 함께 수정합니다.
- 이 I2C 배선 예시를 기존 `nu40-lsm6dso.overlay`와 동시에 사용하지 않습니다.

## 빌드와 업로드

게임용 펌웨어는 NCS/Zephyr 프로젝트입니다. AirBand의 `.ino`나 Arduino 업로드 명령을 여기 적용하지 않습니다. 검토한 overlay와 기존 NCS 3.4.1 도구체인을 사용합니다.

```sh
python3 tools/build-board.py \
  --sdk-root /absolute/path/to/ncs/v3.4.1 \
  --toolchain /absolute/path/to/nordic/toolchain \
  --overlay /absolute/path/to/reviewed-lsm6ds3tr-c.overlay \
  --trace --out .work/nu40-lsm6ds3tr-c
```

이 명령은 컴파일만 합니다. NU40의 부트로더·디버거·flash 영역을 먼저 확인하고, 담당자가 그 장치의 설치 절차로 올립니다. 다른 보드용 설치 스크립트나 erase-all을 사용하지 않습니다. 이 PR에는 실물에 올려 검증한 바이너리가 없습니다.

## 합격 기준: 실제 게임에서 확인

1. firmware/protocol/SDK/game 커밋과 업로드 이미지 해시, 실제 핀·주소·장착 방향을 기록합니다.
2. UART의 센서 설정 성공 메시지 및 trace에서 정지 중 중력/각속도를 확인합니다. 설정 성공만으로 센서 실기 검수가 끝난 것은 아닙니다.
3. **기존 게임**의 설정 → 입력 컨트롤러 → 무선에서 검색·본딩·실제 왕복을 확인합니다. AirBand 웹의 연결 성공을 이 단계의 증거로 쓰지 않습니다.
4. 정지 보정 → 입력 테스트 → 저장까지 완료합니다. 스윙은 기존 v3 20바이트 물리 이벤트를 사용하며, 같은 위→아래 동작도 게임 상황에 따라 서브/스매시 후보로 해석됩니다.
5. 자기 서브 대기에서 위→아래 스윙으로 서브되는지 확인합니다. 랠리에서는 공이 라켓 범위에 있을 때 타격하고, 화면의 입력 성공/헛스윙 이유를 함께 기록합니다. 공을 못 맞혔다는 이유만으로 센서 미인식으로 판정하지 않습니다.
6. 단발 20회와 정지 30초의 입력 횟수·중복·누락, 재연결 후 재보정/입력 복구를 기록합니다. 웹 데모나 버튼 입력으로 센서 성공을 대체하지 않습니다.

## 검증 구분

- 호스트 모의 I2C 검사: ID 불일치, 초기화 I/O 실패, reset 시간 초과, 설정 읽기 불일치, 단위·부호·축 순서, 새 데이터 없음, 부분 읽기 실패 시 출력 유지, 시간 wrap.
- 기존 호스트 검사: 보정·동작 분류·20바이트 이벤트·송신 계약의 회귀 확인.
- **미검증:** Zephyr 보드 컴파일, 정확한 부품/배선, 업로드, 실제 BLE와 게임 스윙. 이 항목들이 남아 있어 PR은 Draft입니다.

코드·Git·PR 관리는 기존 PC에서, 업로드와 실물 게임 테스트는 장비를 연결한 PC에서 진행합니다. 스킨 PR은 이 검수의 선행 조건이 아닙니다.
